## 优化目标

解决"首次搜索/长时间空闲后搜索冷启动缓慢"。体感延迟远超 jieba 的 676ms，主因是 SQLite 页缓存未驻留 + 未启用 mmap。三处改动，全部零外部依赖、零新配置项。

---

## 改动 ①：启用 mmap_size（`engine.py`）

**文件**：`src/copixiv/infrastructure/database/engine.py`
**位置**：`_set_pragmas` 事件处理器（line 41-48）

新增一行 PRAGMA，把主库文件映射进进程虚拟地址空间（508MB 在 64 位下无压力）：

```python
@event.listens_for(engine, "connect")
def _set_pragmas(dbapi_connection, _connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL")
    cursor.execute("PRAGMA synchronous=NORMAL")
    cursor.execute("PRAGMA busy_timeout=10000")
    cursor.execute("PRAGMA foreign_keys=ON")
    cursor.execute("PRAGMA mmap_size=536870912")  # 新增：512MB，覆盖当前库大小
    cursor.close()
```

**取值**：512MB（536870912 字节）。当前库 507.7MB，留 5MB 余量。库若增长超过此值，超出部分自动回退到 read()，不会报错。
**收益**：所有 DB 查询的页访问从 `pread()` syscall 改为指针解引用，随机小读（索引扫描）受益最大。
**风险**：无。可逆，改 PRAGMA 即可。WAL 文件不归 mmap 管，行为不变。

## 改动 ③：调大 cache_size（`engine.py`，同一处）

**文件**：同上
**位置**：同 `_set_pragmas`

在 mmap 那行后再加一行：

```python
    cursor.execute("PRAGMA mmap_size=536870912")
    cursor.execute("PRAGMA cache_size=-50000")  # 新增：每连接 ~50MB pager cache
    cursor.close()
```

**取值**：`-50000`（负数 = KB 单位 → 约 50MB/连接）。
**内存账**：
- 常驻 = 50MB × pool_size(3) = **150MB**
- 峰值 = 50MB × (pool_size 3 + overflow 5) = **400MB**（overflow 用完即释放）
- 你当前 available 5.2G，完全吃得下。

**为什么是 50MB 而非 500MB**：cache_size 是"上限"，缓存的是最近用过的页（LRU），不是整个库。50MB 足够把热索引（`ix_novel_like`、`idx_novel_like_text_id`、FTS 根页等）的 B-tree 内部节点全留住。设成全库大小是 8 倍冗余浪费。

**收益**：连接内的 pager cache 是进程堆内存，Linux 不回收——pool_size 的 3 个常驻连接持续保暖，空闲后不再冷启动。无时间窗口（优于健康检查方案）。
**风险**：堆内存占用。若将来内存紧张，调小这个值即可。与 ① 正交：① 加速访问，③ 抗空闲。

## 改动 ④：修正 jieba 预热（`fts.py`）

**文件**：`src/copixiv/infrastructure/repositories/fts.py`
**位置**：`warm_up()` 静态方法（line 40-44）

当前实现只 `import jieba`（37ms），不触发词典加载。真正的加载发生在第一次 `cut()`（676ms）。改成真正触发一次分词：

```python
@staticmethod
def warm_up() -> None:
    """Pre-load jieba's dict so the first keyword search isn't slow.

    jieba loads its 4.95MB default dict and builds the prefix trie on the
    first ``cut()`` call, not on import. We trigger it here so startup
    pays the cost instead of the first user search.
    """
    try:
        import jieba
        list(jieba.cut("预热", HMM=True))  # 触发词典加载与 trie 构建
    except ImportError:
        pass
```

**调用方不变**：`container.py:86` 已经在调 `FTSManager.warm_up()`，无需改动。它在 `init_database` 之后、应用启动流程中执行，把 676ms 移到启动阶段。
**收益**：进程启动后第一次关键词搜索不再有 676ms 延迟。
**不解决**：空闲后再慢（那是 ①③ 的范畴）；进程被 reload 重启后的冷启动（这种场景 ④ 救不了，除非关掉 `uvicorn.run(reload=True)`，但这超出本次范围，保留现状）。

**附带建议（不在本次改动内）**：`query_builder.py:98` 有一处独立的 `import jieba`，与 FTSManager 的预热脱节。由于 jieba 是单例模块，import 后模块级状态共享，FTSManager 预热完毕后 query_builder 调 `jieba.cut()` 会直接命中已加载的词典，无需额外改动。

## 不做的事

- **② vmtouch / mlock**：你不确定钉死有隐患，且 ③ 已用更简单的方式（堆内存）达成抗空闲。跳过。
- **② 折中（启动预热 + 定期健康检查）**：③ 已覆盖抗空闲，折中方案带来的复杂度（后台任务、mincore/vmtouch 轮询、重新预热 I/O 突发）不值得。若实测 ③ 后仍有冷启动，再单独评估。
- **新增配置项**：三处取值都硬编码合理默认，不往 config.yaml 加字段，避免过度配置化。
- **改 pool_size / max_overflow**：当前 3+5 合理，不动。

改动后可这样验证效果（不在本次改动内，作为后续自查）：
1. 重启服务，首次关键词搜索应感知不到 jieba 延迟（④）
